# الشركات والعضويات والدعوات — مشروع Supabase `cgwnusudjhhxkwnqjzfr`

## 1. البنية الحالية (فحص قراءة فقط)

ملاحظات أمنية في البنية الحالية:

## 2. التصميم المقترح

الترحيل: `supabase/migrations/20261027000100_companies_memberships_invitations.sql` — **طُبّق على cgwn في 2026-10-27**. التراجع: `supabase/proposed/20261027000100_rollback.sql` (يحذف الدعوات وسجل التدقيق والأعمدة المضافة؛ لا يُشغَّل إلا بموافقة).

- يمد `companies` و`company_memberships` القائمين؛ لا نظام عضويات موازٍ ولا نقل بيانات من `safety_*`.
- كل الكتابة عبر دوال `SECURITY DEFINER` تتحقق من المنفّذ وتسجل في سجل التدقيق؛ تُسحب صلاحيات الكتابة المباشرة.
- رمز الدعوة 256 بت عشوائية يُعاد مرة واحدة؛ يُخزَّن SHA‑256 فقط ولا يُقرأ عمود البصمة من الواجهة.

### دورة الدعوة
1. المالك: `platform_create_company` → شركة `pending` + رقم `ORG-xxxxxx` + دعوة `manager` لبريد المدير → يظهر الرابط مرة واحدة مع النسخ/البريد/WhatsApp.
2. المدير يفتح `/invite/<token>` → يُطلب تسجيل الدخول (Google) ثم يعود للرابط → `invitation_preview` يعرض الشركة والدور وتلميح البريد.
3. `accept_company_invitation` يتحقق: الرمز صحيح، معلّق، غير منتهٍ، غير ملغى، لم يُستخدم، البريد الموثّق = البريد المدعو، الحساب ليس مالك المنصة، الشركة غير موقوفة/مؤرشفة → تُنشأ العضوية (أو تُربط بالحساب القائم) كـ`company_manager` أساسي، وتصبح الشركة `active`، وتُعلَّم الدعوة مقبولة.
4. المدير في `/team`: `company_invite_member` لأدوار مشرف/فني/محاسب/أمين مستودع فقط → رابط → القبول بالشروط نفسها ينشئ عضوية واحدة بالدور المحدد.
5. إعادة الإرسال = دعوة بديلة برمز جديد ويُبطل السابق؛ الإلغاء فوري؛ الصلاحية من 1 إلى 720 ساعة.

### الحماية من التلاعب
- الشركة والدور يُقرآن من سجل الدعوة في القاعدة، لا من الرابط أو النموذج.
- معرّف شركة مدير الفريق يُؤخذ من الجلسة، وكل دالة تتحقق `current_company_role(company) = 'company_manager'`.
- المدير الأساسي لا يُعطَّل ولا يُزال ولا يُغيَّر دوره؛ النقل بإجراء `manager_transfer` يتطلب قبول البريد الجديد، ويصبح المدير السابق مشرفًا.
- لا أحد يعدّل عضويته بنفسه. الإزالة لا تحذف الصف (`removed`) للحفاظ على السجلات.
- تغيير بريد عضو = دعوة `email_change` للبريد الجديد؛ العضوية تنتقل للحساب الذي يثبت ملكيته فقط.
- الحذف النهائي للشركة: مؤرشفة + كتابة رقمها + بلا عضويات ولا دعوات مقبولة؛ سجل التدقيق يبقى.

## 3. الإرسال الآلي للدعوات (لاحقًا)
- لا توجد خدمة بريد مهيأة لدعوات التطبيق. بريد Supabase المدمج مخصص لرسائل المصادقة وبحدود إرسال منخفضة ولا يُستخدم لهذه الدعوات.
- للتفعيل لاحقًا: مزود SMTP/API (مثل Resend أو Brevo بخطط مجانية محدودة) + Supabase Edge Function أو Server Action يرسل الرابط وقت إنشائه (لأن الرمز لا يُخزَّن)، مع مفتاح المزود في أسرار الخادم فقط. لم يُنشأ أي اشتراك ولم تُرسل أي رسالة.

## 4. خطوات الاختبار
تحتاج 3 حسابات Google مختلفة: المالك، ومدير الشركة، والفني/المشرف (حساب المالك لا يقبل دعوات الشركات عمدًا).
1. بحساب المالك: `/platform-admin` → «تسجيل شركة صيانة جديدة» → أدخل الاسم وبريد المدير → انسخ الرابط. تحقق أن الشركة «بانتظار قبول دعوة المدير» ولها رقم `ORG-`.
2. في نافذة خاصة: افتح الرابط → سجّل الدخول بحساب المدير → «قبول الدعوة» → تصل إلى `/team`، والشركة أصبحت «نشطة».
3. افتح الرابط نفسه مرة أخرى → «استُخدمت هذه الدعوة من قبل».
4. في `/team`: «دعوة عضو جديد» بدور فني أو مشرف → انسخ الرابط.
5. افتح الرابط بحساب غير المدعو → رسالة البريد المختلف ولا يظهر زر القبول. ثم ادخل بالحساب المدعو → اقبل.
6. في `/team`: غيّر دور العضو، عطّله ثم فعّله، جرّب «إعادة إرسال» ثم تأكد أن الرابط القديم مرفوض، وجرّب «إلغاء».
7. بحساب المالك: أوقف الشركة → يفقد أعضاؤها الوصول؛ أعدها للعمل؛ راجع «سجل التدقيق» في صفحة الشركة.

اختبار آلي محلي لكل ما سبق: `npm run test:invites` (على نسخة محلية مطابقة لبنية المشروع، دون اتصال بالقاعدة الحقيقية).
